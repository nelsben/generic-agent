## Why

Feature revision 2 (FR2), Ben's chapter notes on pattern 05. The session object is "specific to one agent interaction"; he wants "memory records ... and history records in a more agnostic way. So whether I create a task, whether I generate a brief", it is "a build artifact and an outcome that has happened that should persist against that customer for a period of time, potentially for forever". Past outcomes must be "reusable", and there must be "context and history for an agent when the rep opens up the conversation". Covers ledger rows F75, F76, F78 and F80 in docs/plans/feature-revision-2.md.

- **The object:** Customer_Outcome__c in a master-detail to Account, so sharing follows the account (a user who loses the account loses its outcomes; this closes N6, memory outliving access). Set the master-detail so read access to the account is enough to create an outcome (the field's writeRequiresMasterRead set to true, the "Read Only" sharing setting; confirm its meaning in the Metadata API docs and give the reason in the doc), so a rep with read-only access still has the summary recorded; test it Fields: type (from Customer_Outcome_Type__mdt: Summary, Action, Saved answer, with room for more), title, body (the summary text or the action's plain-English result), the related record's Id as text (a task, case or opportunity), the skill and surface that made it, the model used, sentiment score, label and reason (written by BE-36), and an expiry date. Nothing is specific to one agent or one session. **What others see:** a summary is built from what its author could read, so another rep sees the type, date, title of an action, the related record link (Salesforce checks that link itself) and the sentiment label, but not the body, the headline or the sentiment reason, unless that type's record in Customer_Outcome_Type__mdt is marked to share its body (off by default; Ben decides per type). The author always sees everything. The rule sits in one place in Apex with a comment naming F79 (see Field access below for how it is enforced), and the report type leaves out the body, headline and reason fields
- **Retention:** each type's record in Customer_Outcome_Type__mdt sets how long its outcomes live (blank means forever; Summary defaults to forever, others to 2 years). A batch class deletes expired outcomes (in system context, marked per BE-37: it must see every rep's outcomes); scripts/schedule-outcome-retention.apex schedules it, but scheduling it in agent-probe waits for Ben's go
- **Field access (ledger F87, principle 5):** the data-access permission set gives reps no field access to the body, the headline and the sentiment reason, so the rule on what others see cannot be bypassed through a list view, the record page, a report or the API. CustomerOutcomes writes and reads those fields in system context, marked `// system-context:` with its reason per BE-37, and returns them only to the outcome's author or for a type marked to share; every other field, and the record itself, is read and written in user mode, so access still follows the account. Test that a second rep who can see the account gets no body from a user-mode query
- **Writing:** CustomerOutcomes.record(...) in user mode for the record and its other fields, taking one input object with every field above including the sentiment score, label and reason (BE-36 fills them through CustomerSummary and cannot edit this class), called once at the end of a summary (after every model call, as the memory write is today; a failed write is logged and the summary still returns) and exposed as an invocable for the agent and MCP.
