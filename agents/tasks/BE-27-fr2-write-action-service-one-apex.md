## Why

Feature revision 2 (FR2): sellers create follow-ups and updates "verbally or through the chat", along the same path as ask anything. Every write shows a draft and happens only on Confirm. One service serves the panel, the agent and later MCP, per the shape the actions spike (BE-22) chose. Each confirmed action is also an outcome that "should persist against that customer" (Ben's chapter notes on pattern 05), so it is written to the customer outcome store BE-35 built. Covers ledger rows F15, F16, F17, F18 and F75 in docs/plans/feature-revision-2.md. Not dispatched until Ben answers F17 (log a call as a Task or an Event).

- Apex: CustomerSummaryActions with draft(actionType, accountId, Map<String,Object> input) that validates and returns a draft (action, target record label, the fields with labels and values, warnings) with no DML, and commit(draft) that writes it and returns the record Id, a label and a link path. After a successful commit, it records one Action outcome on the account through CustomerOutcomes.record (BE-35; read docs/research/fr2-customer-outcomes.md) with the plain-English result and the new or changed record; a failed outcome write is logged and never undoes the action. An undo removes that outcome too, through CustomerOutcomes.remove (BE-35). Actions: create_task (subject, due date, priority, related contact), create_event (subject, start, end or duration, related contact), log_call (per Ben's F17 answer, which the brain writes onto this card before dispatch; the choice sits in one constant with a comment naming F17), update_contact (only fields named in an allow-list), create_case (subject, description, priority, contact), update_opportunity (stage, close date, next step, amount; open opportunities on the account only). No email drafting
- Free text: draftFromText(accountId, text) turns a typed or spoken sentence (for example 'create a follow-up for next Tuesday') into one of the six actions and its fields through the existing model seam (pattern 04), returning the same draft, or a plain 'not an action' result so the caller can treat it as a question. The model call and any commit never share a transaction. Free text never routes through the agent (ledger F83: the agent is not a way in). Undo: commit returns an undo token; undo(token) within 15 seconds restores the previous values of an update or deletes a record the user just created, in user mode, and refuses after that. Every query and DML runs in user mode, so CRUD, field-level security and sharing apply; a record the user cannot edit gives a plain-English refusal, never a stack trace. Commit happens in its own call, never in the same transaction as a model callout. Dates and people resolve from plain words ('next Tuesday', 'Maria') in the draft step, and anything unresolved comes back as a field for the user to fill, not a guess
