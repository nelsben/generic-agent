## Why

Feature revision 2 (FR2): sellers create follow-ups and updates "verbally or through the chat", along the same path as ask anything. Every write shows a draft and happens only on Confirm. One service serves the panel and later MCP, per the shape the actions spike (BE-22) chose; the agent is not a way in (ledger F83). Each confirmed action is also an outcome that "should persist against that customer" (Ben's chapter notes on pattern 05), so it is written to the customer outcome store BE-35 built. Covers ledger rows F15, F16, F17, F18 and F75 in docs/plans/feature-revision-2.md.

- Apex: CustomerSummaryActions with draft(actionType, accountId, Map<String,Object> input) that validates and returns a draft (action, target record label, the fields with labels and values, warnings) with no DML, and commitDraft(draft) that writes it (`commit` is a reserved word in Apex and does not compile; BE-22) and returns the record Id, a label and a link path. After a successful commit, it records one Action outcome on the account through CustomerOutcomes.record (BE-35; read docs/research/fr2-customer-outcomes.md) with the plain-English result and the new or changed record; a failed outcome write is logged and never undoes the action. An undo removes that outcome too, through CustomerOutcomes.remove (BE-35). Actions: create_task (subject, due date, priority, related contact), create_event (subject, start, end or duration, related contact), log_call (writes an Event, as Ben said in F17; the choice sits in one constant with a comment naming F17, so 'make it a Task' is a one-line change. BE-22 measured both shapes: a completed Task with subtype Call and a 15-minute Event both land in ActivityHistories, and the standard LogACall quick action targets Task; the choice stays Ben's), update_contact (only fields named in an allow-list), create_case (subject, description, priority, contact), update_opportunity (stage, close date, next step, amount; open opportunities on the account only). No email drafting
- Free text: draftFromText(accountId, text) turns a typed or spoken sentence (for example 'create a follow-up for next Tuesday') into one of the six actions and its fields through the existing model seam (pattern 04) with its own prompt file (an AgentPrompt_Action static resource; if BE-33 has merged it also gets an Agent_Prompt_Setting record, and if not it uses the seam's defaults and the hand-back says so), returning the same draft, or a plain 'not an action' result so the caller can treat it as a question. Start the prompt from the system prompt BE-22 ran (systemPrompt() in spikes/actions/router.apex). Before the model call, a filler-skipping first-word verb pre-check (BE-22's proposal, checked offline only against its own nine requests) returns 'not an action' at no model cost; matching a verb anywhere in the text is wrong (a question with 'open' in it misroutes). Pin the pre-check with at least 30 phrasings written fresh for this card, actions and questions both, and say in the hand-back which ones it misses. The model fills a person the request did not name even though the prompt forbids it (BE-22, 5 of 5 drafts): the resolve step in code is the guard, and an unmatched name comes back unresolved, never guessed. The model call and any commit never share a transaction: a model call after DML throws CalloutException (BE-22), so draft and commitDraft are always separate server calls. Free text never routes through the agent (ledger F83: the agent is not a way in). Undo is for updates only: the commit of an update returns an undo token that carries the previous values itself, so nothing is stored between the two calls; undo(token) within 15 seconds restores those values in user mode under the same allow-list as commit (a changed token can do nothing the user could not do by an update), and refuses after that. A created record has no undo; the result shows the record so the user can open it. Every query and DML runs in user mode, so CRUD, field-level security and sharing apply; a record the user cannot edit gives a plain-English refusal, never a stack trace. Commit happens in its own call, never in the same transaction as a model callout. Dates and people resolve from plain words ('next Tuesday', 'Maria') in the draft step, and anything unresolved comes back as a field for the user to fill, not a guess
